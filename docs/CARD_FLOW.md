# 卡片狀態流轉（完整規格）

> 這份是看板（board/）與排隊器（jet/）之間「一張卡從開到合併」的唯一依據。
> 兩邊的實作、測試、文件都以這份為準；要改行為先改這份。
>
> 前提：這份描述的是排隊器設定成「先審後測」＋「外部來源」（見 DESIGN.md 第 3 節的兩種模式）、並搭配看板使用時的行為。排隊器設成「不分先後」或不接看板時，不適用這份。

## 1. 角色

| 角色 | 能做的動作 |
| --- | --- |
| 管理者 | 發卡、設父卡與先後、放棄卡、強制收回卡、重測 |
| 開發者 | 領卡、還卡、送審、放棄自己的卡 |
| 審查者 | 放行、退回、撤回放行、重測 |
| 排隊器 | 回報測試與合併的每一步 |
| 看板的定時器 | 卡住太久時提醒管理者 |

每張卡對應一條分支，分支名在領卡時由看板給定，之後不變。

## 2. 八個狀態

| 代號 | 顯示 | 意思 |
| --- | --- | --- |
| `new` | 剛開卡 | 發了卡，沒人領 |
| `developing` | 開發中 | 有人領了，還沒送審（或送審後內容又變了） |
| `reviewing` | 審查中 | 已送審某個版本，等審查者 |
| `selftesting` | 審查通過自測中 | 已放行；排隊器在等空槽、等父卡、或正在自測 |
| `batching` | 自測完畢批測中 | 自測綠；在排隊或正在批測 |
| `merged` | 已合併 | 進了主線（結局） |
| `rejected` | 退回 | 審查不過、自測紅、批測紅、撞檔，附原因 |
| `dropped` | 放棄 | 不做了（結局） |

## 3. 卡片上存什麼

看板只存事實，狀態是從事實算出來的，不另外存一份：

- `status`：`open`／`claimed`／`dropped`
- `owner`：誰領的
- `branch`、`parent`（父卡）
- `submitted_sha`：送審的版本
- `approved_sha`：放行的版本（一定等於當時的 `submitted_sha`）
- `review_reject`：審查退回的原因（有值表示被審查退回）
- `retest`：重測計數（每按一次重測加一）
- `queue`：排隊器對「目前這次放行」最後回報的階段、原因、紅項

### 狀態怎麼算（由上往下，先符合的算數）

1. `status` 是 `dropped` → `dropped`
2. 排隊器回報過這條分支已合併 → `merged`
3. `status` 是 `open` → `new`
4. `review_reject` 有值 → `rejected`
5. 沒有 `submitted_sha` → `developing`
6. 沒有 `approved_sha` → `reviewing`
7. `queue` 的階段是退回、撞檔或暫停 → `rejected`
8. `queue` 的階段是自測綠、排隊或批測中 → `batching`
9. 其他（排隊器還沒回報、等空槽、等父卡、自測中）→ `selftesting`

## 4. 完整轉移表

沒列在某個狀態底下的動作，看板一律拒絕（回 409 並說明現在是什麼狀態）。同一個動作重複送，結果一樣，不算錯。

### `new` 剛開卡

| 事件 | 誰 | 結果 | 附帶動作 |
| --- | --- | --- | --- |
| 領卡 | 開發者 | `developing` | 記 `owner`；給定 `branch` |
| 放棄 | 管理者 | `dropped` | |

### `developing` 開發中

| 事件 | 誰 | 結果 | 附帶動作 |
| --- | --- | --- | --- |
| 送審（帶版本） | 開發者 | `reviewing` | 記 `submitted_sha`；通知審查者 |
| 還卡 | 開發者、管理者 | `new` | 清 `owner`；分支名保留 |
| 放棄 | 開發者、管理者 | `dropped` | |
| 太久沒動 | 定時器 | 不變 | 提醒管理者 |

### `reviewing` 審查中

| 事件 | 誰 | 結果 | 附帶動作 |
| --- | --- | --- | --- |
| 放行（帶版本） | 審查者 | `selftesting` | 版本必須等於 `submitted_sha`，否則拒絕；放行的人不能是領卡的人；記 `approved_sha`，清空 `queue` |
| 退回（帶原因） | 審查者 | `rejected` | 記 `review_reject`；通知開發者 |
| 再送審（新版本） | 開發者 | `reviewing` | 更新 `submitted_sha` |
| 還卡 | 開發者、管理者 | `new` | 清 `owner`、`submitted_sha` |
| 放棄 | 開發者、管理者 | `dropped` | |
| 太久沒審 | 定時器 | 不變 | 提醒管理者 |

### `selftesting` 審查通過自測中

| 事件 | 誰 | 結果 | 附帶動作 |
| --- | --- | --- | --- |
| 自測綠 | 排隊器 | `batching` | |
| 自測紅或逾時 | 排隊器 | `rejected` | 記原因與紅項；通知開發者 |
| 跟主線撞檔 | 排隊器 | `rejected` | 記撞哪些檔；通知開發者 |
| 內容變了 | 排隊器 | `developing` | 清 `submitted_sha`、`approved_sha`、`queue`；通知開發者要重新送審 |
| 父卡擋住（父卡被放棄或不存在） | 排隊器 | 不變 | 通知管理者 |
| 撤回放行 | 審查者 | `reviewing` | 清 `approved_sha`、`queue` |
| 退回（帶原因） | 審查者 | `rejected` | 清 `approved_sha`；記 `review_reject` |
| 再送審（新版本） | 開發者 | `reviewing` | 更新 `submitted_sha`；清 `approved_sha`、`queue` |
| 放棄 | 開發者、管理者 | `dropped` | |

### `batching` 自測完畢批測中

| 事件 | 誰 | 結果 | 附帶動作 |
| --- | --- | --- | --- |
| 合併 | 排隊器 | `merged` | |
| 批測找出是它紅 | 排隊器 | `rejected` | 記原因與紅項；通知開發者 |
| 跟主線撞檔 | 排隊器 | `rejected` | 通知開發者 |
| 沒輪到、同批別人紅、父卡是兇手 | 排隊器 | 不變 | |
| 內容變了 | 排隊器 | `developing` | 同上 |
| 撤回放行 | 審查者 | `reviewing` | 清 `approved_sha`、`queue` |
| 退回（帶原因） | 審查者 | `rejected` | 清 `approved_sha`；記 `review_reject` |
| 再送審（新版本） | 開發者 | `reviewing` | 更新 `submitted_sha`；清 `approved_sha`、`queue` |
| 放棄 | 開發者、管理者 | `dropped` | |

### `rejected` 退回

| 事件 | 誰 | 結果 | 附帶動作 |
| --- | --- | --- | --- |
| 改好再送審（新版本） | 開發者 | `reviewing` | 更新 `submitted_sha`；清 `approved_sha`、`review_reject`、`queue` |
| 重測（內容不改） | 審查者、管理者 | `selftesting` | 只有被排隊器退回時可用；`retest` 加一、清 `queue`；放行保留 |
| 只是重新接到最新主線、內容沒變 | 排隊器 | `selftesting` | 只有被排隊器退回時會發生；放行保留，不用重審 |
| 還卡 | 開發者、管理者 | `new` | 清 `owner`、送審與放行紀錄 |
| 放棄 | 開發者、管理者 | `dropped` | |
| 太久沒動 | 定時器 | 不變 | 提醒管理者 |

同一個版本在批測被找出是它紅兩次，排隊器會暫停它：仍顯示 `rejected`，並標明「已暫停」。要再跑只能送新版本或按重測。

### `merged` 已合併、`dropped` 放棄

結局。任何動作都拒絕。合併後想改，另開一張卡。

## 5. 四條一定要守的規則

1. **放行跟著版本走。** 放行記的是「這個版本」。分支出現內容不同的新版本，放行自動失效，卡片回到開發中。只是重新接到最新主線、內容沒變的，放行繼續有效。內容有沒有變，由排隊器用內容指紋判斷，看板不判斷。
2. **過期的回報不算數。** 排隊器每筆回報都帶「它是依哪一次放行算的」（`approved_sha`）和重測計數。看板只接受跟卡片現在的放行、現在的重測計數相符的回報，其餘丟掉。這樣舊版本晚到的「退回」不會把已經重新送審的卡打回去。
3. **推上主線前再確認一次。** 排隊器在把一批推上主線之前，重新向看板拉一次清單。這一批裡只要有一條已被撤回、放棄或內容變了，這次結果就不推：能改推「不含它的最大綠點」就推那個，不能就整批重排。已經合併的不回頭，晚到的撤回會被看板拒絕。
4. **拉不到看板時，只測不合。** 推主線前那一次重拉必須成功，失敗就不推、下一輪再試；自測和批測照上一次的清單繼續。另外清單超過設定的時間（預設 10 分鐘）沒更新成功時，連新的批測也不開，等看板恢復。

## 6. 看板給排隊器的清單

排隊器定時拉。每筆是一張「已領、未合併、未放棄」的卡：

| 欄位 | 意思 |
| --- | --- |
| `branch` | 分支名 |
| `parent` | 父卡的分支名（沒有就省略；父卡已合併也省略） |
| `parent_status` | 父卡不在這份清單上時才有：`open`（父卡還沒人領或被還卡）或 `dropped`（父卡被放棄） |
| `approved_sha` | 放行的版本（沒放行就省略） |
| `retest` | 重測計數 |

排隊器只管清單上的分支；只有帶 `approved_sha` 的才會自測。`retest` 比上次看到的大，就把這條分支的退回與暫停清掉，從待自測重來。

## 7. 排隊器回報給看板的事件

每筆帶：分支、事件種類、分支當時的版本、依據的 `approved_sha`、`retest`、原因、紅項清單、時間、事件編號（看板用來去重）。

- 「依據的 `approved_sha`、`retest`」是這次測試**開跑時**的值，不是送出事件當下的值。
- 事件編號要跨資料庫重置仍唯一（帶資料庫建立時產生的識別碼）。
- 「合併」是既成事實：看板收到合併事件一律接受，不做過期比對。

| 事件 | 看板的 `queue` 階段 | 對應狀態 |
| --- | --- | --- |
| 開始等自測、等父卡、自測中 | 自測中 | `selftesting` |
| 自測綠、排隊、批測中 | 批測中 | `batching` |
| 自測紅、逾時、批測退回 | 退回（附紅項） | `rejected` |
| 撞檔 | 退回（附撞的檔） | `rejected` |
| 暫停（批測紅兩次） | 退回＋已暫停 | `rejected` |
| 內容變了 | 清空 | `developing` |
| 父卡擋住 | 自測中＋註記 | `selftesting` |
| 合併 | 已合併 | `merged` |

排隊器自己的問題（當機、暫停、機器異常）不是任何一張卡的事件，另外通知管理者，卡片狀態不動。

## 8. 誰會被通知

| 發生什麼 | 通知誰 |
| --- | --- |
| 卡片進審查中 | 審查者 |
| 退回（不論誰退的）、內容變了要重新送審 | 領卡的開發者 |
| 父卡擋住、卡片被暫停、卡住太久、排隊器自己出問題 | 管理者 |
| 合併 | 不通知，卡片自己顯示 |

通知會攢幾分鐘、同一個對象合成一則。

## 9. 父卡與子卡（堆疊）

卡片的 `parent` 表示「這張卡接在另一張還沒合併的卡後面」，可以一路接下去。子卡的分支從父卡的分支開出來。

- 子卡可以在父卡合併前就領、開發、送審、放行；也可以比父卡先被放行，但不會先合併。
- **審查**：只看子卡比父卡多出來的那一段。
- **自測**：疊在主線加整條父鏈上測。排隊器等父卡「已合併或也在隊伍裡」才測子卡；等的期間子卡停在審查通過自測中。
- **批測**：同一批裡父卡一定排在子卡前面；整條鏈可以在同一批合併。父卡不在最大綠點內，子卡就不在。
- **內容指紋只算子卡自己那一段**（相對於父卡的差異）。父卡改了內容、子卡重新接到新父卡上，只要子卡自己那一段沒變，放行繼續有效、不發「內容變了」；有變才回到開發中。
- 父卡被退回或內容變了：子卡回到待自測（看板上仍是審查通過自測中），父卡好了再測。
- 批測時兇手是父卡：子孫一起留到下一批，不算它們紅，不計入「批測紅兩次」。
- 父卡被放棄或不在清單上：子卡被擋住，通知管理者改父卡（管理者可以把 `parent` 改成別張卡或清空；改了之後放行保留，排隊器從待自測重來）。
- 父卡合併：子卡變成普通卡（清單上省略 `parent`），放行繼續有效。
- **父卡沒進主線，子卡絕不單獨進。** 清單上寫了 `parent` 的卡，只有在父卡已合併、或父卡在同一批排在它前面時才能合併。父卡的分支還沒推上來、父卡還沒人領、父卡被還卡：子卡一律等（不當成沒有父卡）。只有 `parent_status` 是 `dropped` 才發「父卡擋住」。
- **子卡必須接在父卡現在的版本上。** 父卡還沒合併時，父卡目前的版本必須是子卡的祖先；不是（父卡改版了、子卡還沒重新接上）就不測不合，子卡退回，原因寫「父卡已更新，請重新接到父卡上」，通知開發者。重新接上後自己那一段沒變，放行繼續有效。
- 不允許循環；父卡必須存在且不是已放棄的卡，否則看板拒絕設定。

## 10. 純文件的卡

走同一條線。審查通過後，排隊器判定是純文件就不測，直接合併：看板上會從審查通過自測中直接變成已合併。有父卡的純文件卡，要等父卡合併了才合。
